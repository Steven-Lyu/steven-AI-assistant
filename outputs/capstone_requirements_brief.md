## 1. 课题原文与目标

导师提供的 capstone topic：

> Develop an AI personal assistant capable of automating various tasks, such as scheduling appointments, managing emails, and organizing files. The goal is to create a versatile tool that can significantly enhance productivity and efficiency.

据此，项目目标是开发一个能协助用户处理多种个人事务的 AI 助手。预约安排、邮件管理、文件整理是示例场景，并不意味着第一个 milestone 必须同时完成全部场景。

## 3. 产品定位

用户通过图形界面提出或选择任务，查看助手的执行状态、关键步骤和结果，并对有影响的操作作出确认。界面应围绕个人事务组织信息，不应仅是一个通用聊天框。

长期功能方向：

1. **日程与预约：**理解安排需求、提出时间建议、在用户确认后创建或修改事件。
2. **邮件：**整理或概述邮件、起草回复、在用户确认后发送或执行批量操作。
3. **文件：**识别和分类文件、提出整理方案、在用户确认后移动或重命名文件。

文件整理已选为第一条真实任务流程；日程和邮件仍是后续方向，当前界面明确标为未接入。

## 4. 第一阶段（Milestone 1）建议范围

### 核心交付

- 一套可操作的 GUI：清楚展示任务入口、任务详情、执行进度、结果，以及用户需要处理的确认或错误。
- 有目的的交互动画：表现任务从「已提交 → 正在理解／执行 → 等待确认 → 完成／失败」的状态变化；动画帮助用户理解系统行为。
- Codex 后台接入：文件整理任务能从用户操作开始，经应用服务层与 Codex app-server 处理，最终把真实结果返回界面。sample 文件流程已跑通，已增加用户选择真实文件夹的流程。
- GUI 权限审批：当 Codex 请求执行命令、修改文件或扩大访问权限时，显示请求内容及作用范围，允许用户批准或拒绝，并把决定返回 app-server。
- 可扩展的页面与任务结构：未来能够加入日程、邮件和文件等模块，而不必重做整个 GUI。

### 建议暂缓

- 同时完成所有任务类型及所有第三方服务集成。
- 在第一阶段开发完整的 multi-agent 系统。
- 在缺少用户场景和评估依据时自行训练模型或重写智能体执行框架。

这些是控制第一阶段范围的建议，不是导师的禁止项。

## 5. 用户体验与动画要求

第一阶段的关键体验应覆盖：

1. **发起任务：**用户知道助手能做什么，并能输入需求或选择预设动作。
2. **看到过程：**界面及时显示当前状态和有意义的进度，避免长时间无反馈。
3. **保持控制：**涉及发送邮件、修改日程、移动文件等实际更改时，向用户展示将发生什么并请求确认。
4. **理解结果：**明确显示完成内容、失败原因及可采取的下一步。

动画可用于页面切换、任务状态转换、步骤推进、确认提示和完成反馈。应保持节制，不能用动画掩盖真实等待或伪造任务进度；提供减少动态效果的支持。

设计备忘：缓慢变化的首页背景目前只是候选想法，是否加入取决于前端整体结构。文件整理已成为首个真实场景，当前界面已使用文件卡片的归位动画；扩展到真实文件时，动画仍应对应实际任务状态。

### 真实文件夹扩展：初版方案与边界（后续由下文多层方案扩展）

1. 用户在 GUI 点击 **Browse**，由本地应用服务打开 Windows 系统文件夹选择窗口。服务取得绝对路径，界面显示选中目录和扫描概要；取消选择时不创建任务。
2. 仅处理用户本次明确选择的目录。沿用当前由 Node 应用服务扫描、校验和移动文件的结构；浏览器的目录句柄方案暂不采用。初版真实文件流程建议只处理所选目录第一层的普通文件，并清楚说明跳过或拒绝子目录、链接和不适合处理的项。
3. Codex 先给出分类方案。GUI 显示源文件与目标分类，用户确认后才执行移动；Codex 权限审批仍与业务确认分开。
4. 执行前重新核对所选目录和文件状态，拒绝越出所选目录的路径、目标重名与状态已变化的文件，并在失败时清楚呈现已完成和未完成的操作。当前 sample 实现的保护逻辑须针对真实文件重新检查。
5. 当前实现会读取整个文件来计算哈希。接入真实大文件前，应改为流式校验或等效的低内存方案。默认只把分类所需的名称、大小等信息提供给 Codex；读取或传送文件正文需要单独的产品决定。

**用户确认（2026-11-11）：**分类子目录位于所选目录内部；不提供独立输出目录。用户随后决定分类名不再限定为 Study / Work / Life / Other，Codex 可依照输入偏好提出学科等分类。分类名仍须是安全的单层 Windows 文件夹名，并在移动前由服务校验。

**实现边界：**首版每次最多 200 个普通文件，跳过子目录、符号链接/junction、硬链接与点文件。Windows 原生选择器使用项目内 C# 源码和系统 .NET Framework 编译器，首次运行产物放在忽略的 `work/native/`，不修改 PowerShell 策略。分类只传名称和大小；校验在本地流式计算 SHA-256。确认后以独占硬链接再移除原路径完成同卷移动，保留文件内容与元数据；不支持硬链接的文件系统安全失败。失败时保留已完成操作，不做猜测式回滚，并列出已移动、未移动和需要检查两个位置的文件。外部程序并发修改和进程意外终止仍不属于事务保证。

### 多层目录整理方案（已实现，2026-11-12）

**用户决定：**递归检查文件及原有分类，按用户指定的标准统一归类；不同来源的同类文件直接汇总到 `所选目录/Organized/类别/文件名`。同名文件用编号区分，保留扩展名。以下为已采纳的需求；对应实现与验证见 `recursive_organization_verification.md`。分类判断、异常处理等补充规则属于产品设计建议，不属于导师新增要求。

#### 整理范围选项（用户决定，已实现）

在前端 **How would you like them organized?** 输入框下方、生成方案按钮之前，增加一个复选框。页面初始化时**默认勾选**，含义为“只整理所选文件夹第一层的文件”。网页保持英文，建议标签为 **Only organize files directly in this folder**，辅助说明为 **Uncheck to include files in subfolders.**

| 复选框状态 | 整理范围 |
| --- | --- |
| 勾选（默认） | 只处理所选目录第一层的合格普通文件，跳过子目录及其中的文件。 |
| 取消勾选 | 同时处理所选目录第一层和各级子目录内的合格普通文件，应用下文的递归分类、汇总和同名编号规则。 |

取消勾选意味着纳入子文件夹里的文件，不意味着移动文件夹本身。两种模式均沿用既有文件资格校验和用户确认流程；递归模式仍须遵守深度、数量、输出目录排除等限制。

实现时，范围选择须传给服务端并绑定到扫描清单与任务；请求未提供范围时默认单层。切换选项后重新扫描并更新文件数量和范围提示，旧清单及旧方案不能继续执行。任务已提交后禁用该选项，待任务完成或取消后再调整。验收时须验证后台实际处理范围与复选框一致。

#### 标准示例与分类判断

选中 `test`，其下 `files1`、`files2` 都有多种文件，用户取消勾选单层选项并选择按科目整理。若两者均含 `IELTS Reading.docx`，且都归为 English，预览应展示：

```text
test/files1/IELTS Reading.docx → test/Organized/English/IELTS Reading 1.docx
test/files2/IELTS Reading.docx → test/Organized/English/IELTS Reading 2.docx
```

目标中不再嵌入 `files1` 或 `files2`。原相对路径仍保留在计划和结果报告中，用于识别来源、追踪操作；不能用文件名作为唯一标识。

扫描后先根据用户的分类标准、相对路径和文件名判断现有分类是否合理。文件夹名只能作为线索：例如 `English` 内可能混有数学文件，而 `files1` 内也可能全是英语资料。建议逐文件给出“可沿用类别、需要重新分类、无法判断”的结论和简短理由，再汇总目录情况；不能仅凭目录名断言全部文件已分类好。

“类别已经正确”与“已位于最终目标位置”分别处理。建议规则：来源目录中已正确分类的文件可复用类别，仍在预览中明确是否汇总到 `Organized`；用户可排除不希望移动的文件。已经位于本应用输出目录的文件默认不重新分类。名称信息不足时标为待检查，允许用户指定类别或排除，不擅自读取文件正文；全部文件都不需要处理时展示无需操作。

#### 流程与命名规则

1. **按所选范围扫描。**默认扫描第一层，取消勾选单层选项时递归扫描。记录每个文件的 `relativePath`、名称、大小和本地校验信息。限制深度、文件总数及耗时，支持进度与取消；沿用跳过链接、junction、硬链接、点文件的边界，递归时也跳过点目录。扫描不修改文件，跳过及未扫描的范围应完整展示。
2. **分类计划。**Codex 接收相对路径、名称和大小，以相对路径关联每个文件，提出类别和理由。类别仍须是安全的单层目录名。每个输入文件须有明确处置（移动、保留或待检查），服务验证没有重复、遗漏或未知源文件；不接受模型生成的任意绝对路径。
3. **服务统一分配目标名。**分类完成后，本地服务汇总本次计划与已有目标目录，确定全部目标名称。若同一类别中本批次有多个同名文件且目标空闲，则按固定的源相对路径排序，全部加空格和编号，从 `1` 开始；保留原扩展名。同名但目标类别不同不需要编号。唯一且目标名空闲的文件保留原名。
4. **避免编号再次冲突。**目标内已有文件和目录、本批次其他文件的原名以及已分配目标名都参与占用检查。先预留可原名保留的文件名，再给冲突组分配最小可用正整数；例如已有或本批次另有 `IELTS Reading 1.docx` 时跳过该名称。不改名或覆盖既有目标文件。编号只用于解决目标冲突，不表示版本先后或内容优劣。
5. **完整预览后一次确认。**展示相对源路径、最终目标路径、改名前后名称及改名原因，汇总移动、重命名、保留、待检查和跳过数量。用户调整类别或排除文件后重新计算命名；只执行用户确认的最终计划。UI 中当前“名称保持不变”的说明需要随此功能更新，Codex 权限审批仍与产品确认分开。
6. **执行与报告。**执行前检查文件及各层父目录身份、哈希、目标目录和目标名占用情况，保证路径仍在选中范围内。若目标在确认后被占用，停止并要求刷新方案，不在执行时悄悄换成另一个编号。保留不覆盖目标、部分失败不猜测回滚的原则；结果报告记录原路径与最终路径，空来源目录暂不删除。
7. **输出目录管理。**`Organized` 位于所选目录内，后续递归扫描不把它作为来源，但规划时仍检查其中的目标名称占用。不能仅凭名称认定它由本应用创建；若同名目录归属不明、同名位置是文件或路径包含链接，应提示冲突并阻止执行。输出目录识别须跨应用重启有效，避免下次重复整理或产生 `Organized/Organized`。

#### 需一并覆盖的特殊情况（建议默认规则）

| 情况 | 预期处理 |
| --- | --- |
| 同名但内容不同；同名且内容相同 | 两种情况都保留各自文件并按冲突规则编号。不得根据名称、大小或哈希自动删除、合并文件；内容去重属于另一个功能。 |
| 不同名但内容相同 | 默认保留原名并分别处理，不自动去重。 |
| `Notes.docx` 与 `notes.docx`、类别 `English` 与 `english` | 按保守的 Windows 大小写不敏感规则检查占用；同义类别如 English 与英语建议在预览前统一，无法确定时交用户调整。 |
| `IELTS Reading.docx` 与 `IELTS Reading.pdf` | 完整文件名不同，可在同一类别保留；无扩展名文件在名称末尾加编号，多重扩展名（如 `.tar.gz`）应作为整体保留。扩展名识别规则在实现时固定并测试。 |
| 文件名本身已有数字或编号 | 将原文件名作为完整基础名，不猜测或剥离用户原有数字；必要时再次追加编号，并明确显示最终名称。 |
| 文件名加编号后过长、目标路径过长或包含不支持的名称 | 在执行前标为阻塞项，允许调整目标名或排除；不能静默截断名称或等到部分移动后才发现。 |
| 来源目录只部分分类正确，或文件可能属于多个科目 | 逐文件评估，不整目录放行；有歧义的文件待检查。每个源文件最多移动到一个目标，不自动复制到多个类别。 |
| 代码项目、网页及资源、成组数据等存在相对路径依赖 | 平铺可能破坏文件间引用。建议对可识别的关联文件组默认排除并提示原因；未来可增加整体保留策略，不能声称已能识别所有依赖。 |
| 无权限、文件被占用、同步占位文件或不支持当前移动方式的文件系统 | 能提前发现的在预览前报告；执行时失败则记录实际结果。不为分类自动下载云端内容或改变文件访问权限。 |
| 超出扫描上限或部分子目录无法读取 | 标明未扫描范围；不得把不完整清单呈现为整个目录已整理。只允许用户明确确认已扫描范围后规划，或缩小范围重新扫描。 |
| 预览后有新增、删除、改写文件或目录被替换 | 计划失效并提示重新扫描；已开始执行时保留已完成记录，报告未完成及需人工检查的位置。 |
| 第二次运行、改变分类标准或程序中途退出 | 默认排除既有输出；重新分类输出需单独明确选择。保存可追踪的执行记录，未完成任务先核对磁盘实际状态，不盲目重放移动或继续编号。 |

#### 后续实现的验收重点

- 复选框位于指定输入框下方且默认勾选：勾选时不扫描或整理子目录内文件，取消勾选后第一层及子目录文件均纳入；切换范围后旧清单和旧方案失效，界面数量与后台范围一致。
- 两至三层目录中的混合文件能按科目汇总；上面的双 `IELTS Reading.docx` 示例得到 `1.docx`、`2.docx` 两个目标，内容各自保留。
- 同名文件三个以上、已有目标名称、本批次自带编号名称、大小写差异都不会覆盖或重复分配目标名；相同清单与目标状态生成稳定的编号。

- 输出目录排除、应用重启后的识别、扫描范围不完整、关联文件组和中断恢复都有明确行为；默认深度与文件量上限在实施时确定并记录。

## 6. 初步系统结构

```text
用户
  ↓
自建 GUI（任务输入、状态展示、确认、结果）
  ↓
应用服务层（任务状态、app-server 通信、权限请求转发、数据连接）
  ↓
本地 Codex app-server（智能体执行、事件、Codex 权限审批）
  ↓
任务工具／数据源（日历、邮件、文件等；按阶段接入）
```

这里的“自己的后台”与“使用 Codex”可以并存：应用服务层处理产品逻辑、数据连接和 GUI 与 app-server 之间的通信，Codex 处理智能体执行。是否需要在后续研究中替换或比较智能体方案，由导师要求和研究问题决定。账户授权、运行环境和费用条件仍需在实际搭建时核对。

**两类确认应分别设计：**Codex 权限审批来自 app-server，控制它能否执行特定命令、文件更改或访问请求；产品层操作确认让用户审查将发送的邮件、将移动的文件等实际业务结果。即使视觉上共用确认组件，触发条件和回应对象也不同。app-server 的审批请求和执行事件应经应用服务层传给 GUI，用户决定再由应用服务层回传；不能只在界面上改变状态而没有回应后台。

参考：[OpenAI 官方文档：Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)、[Codex app-server 协议](https://learn.chatgpt.com/docs/app-server)。具体协议字段以实现时的官方文档和所用版本为准。
